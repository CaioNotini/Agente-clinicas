# Relatório de Inspeção

Inspeção concluída. Esta foi uma tarefa somente de leitura: nenhum arquivo foi alterado (`git status` seguiu limpo do início ao fim). Segui o `CLAUDE.md` (princípios, `status.md`, depois estudo/arquitetura/etapas/ADRs/código) antes de concluir.

## 1. Bugs encontrados

### [ALTA] `docs/status.md` afirma algo que é falso sobre a etapa 0

A linha `"Etapa 0... Sem FAQ nem base fictícia no repositório (conforme D5)"` não é verdade: `docs/fake_clinic/` existe desde o commit `d1b0d68` (13/10), com `clinica.md` (201 linhas), `FAQ.md` (93 linhas, perguntas categorizadas) e `pergs_bloqueadas.md` (91 linhas, com casos de `clinico_bloqueado`, `urgencia` e forma indireta).

O conteúdo é substantivo, não um placeholder. `status.md` é a fonte de verdade do estado e está desatualizado.

### [ALTA] `.env.example` incompleto — quebra o setup local

`app/config.py` exige `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `APP_DB_USER`, `APP_DB_PASSWORD` (lança `RuntimeError` se faltar alguma).

`.env.example` só lista `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`, `DB_NAME`. Quem copiar o exemplo literalmente não consegue rodar a aplicação.

### [ALTA] `app/db/models.py` desalinhado do schema real — risco para a próxima migration

`migrations/env.py` usa `Base.metadata` (ou seja, `models.py`) como `target_metadata` para autogenerate.

Mas `models.py` só define 8 das 14 tabelas com `tenant_id`: faltam `profissional_servicos`, `regras_agendamento`, `pacientes_contatos`, `handoffs`, `consents`, `privacy_requests`, e falta a coluna `telefone_plantao` em `Clinica`.

Se alguém rodar `alembic revision --autogenerate` nas próximas etapas, o Alembic vai propor `DROP TABLE`/`DROP COLUMN` para tudo isso.

### [MEDIA] Nomes divergentes entre o documentado e o real na base fictícia

Esperado (`etapas.md`/`estudo.md`, etapa 0): `docs/base_ficticia/{clinica.md, faq.md, perguntas_bloqueadas.md}`.

Real: `docs/fake_clinic/{clinica.md, FAQ.md, pergs_bloqueadas.md}`.

Os próprios cabeçalhos desses arquivos citam `./faq.md` e `./perguntas_bloqueadas.md` — nomes que não existem no disco, ou seja, link cruzado quebrado dentro dos próprios arquivos.

Também não há link a partir de `status.md`, violando a regra dos dois cliques do `CLAUDE.md`.

### [MEDIA] Referência pendurada a "ADR 0003"

`docs/etapas.md`, linha 100, cita `"ADR 0003"` como base da etapa 2 (já concluída), mas só existem `0001-alembic.md` e `0002-contas-de-banco.md` em `docs/decisions/`.

### [MEDIA] Acoplamento frágil e não documentado em `ci.yml`

O passo `"Definir senha de app_clinicas"` faz `ALTER ROLE :"app_user" PASSWORD :'app_pw'`, usando o valor do secret `APP_DB_USER` como nome da role.

A migration `21bc40ab245c` cria a role com nome fixo `app_clinicas`. Isso só funciona se o secret `APP_DB_USER` for literalmente a string `"app_clinicas"` — não há comentário, ADR ou validação que amarre essa convenção.

### [MEDIA] `/health` não verifica nada de fato

`app/main.py` retorna sempre `{"status": "healthy", "database": "healthy"}`, fixo, sem consultar o banco.

`tests/test_health.py` aceita `"healthy"` ou `"unhealthy"`, mas nenhum teste força o endpoint a checar a conexão real — dá falso sinal de saúde do banco mesmo que ele esteja fora.

### [BAIXA] `requirements-dev.txt`: `pytest-timeout` sem versão fixa

`pytest-timeout` está sem versão fixa e com espaço em branco sobrando na linha. Todo o resto do arquivo é pinado com `==`.

### [BAIXA] `docs/decisions/README.md` termina com uma cerca de código solta/duplicada

Há uma cerca de código extra (` ``` `) nas últimas linhas, deixando um bloco Markdown vazio pendente.

## 3. Resumo da etapa ativa

O projeto está entre a etapa 2 (concluída) e a etapa 3 (não iniciada), conforme `status.md`.

A etapa 2 está bem implementada e testada:

- Schema multi-tenant completo.
- RLS com `FORCE` e policy `isolamento_tenant` nas 14 tabelas corretas.
- Separação de roles (`app_clinicas`, `scheduler_service`, `cnotini`) alinhada ao ADR 0002.
- Suíte de isolamento com 56 testes cobrindo leitura, escrita cruzada, update/delete cruzado e ausência de tenant.

Tudo isso está consistente com o que a documentação descreve.

Os pontos fora do planejado são:

1. O modelo ORM (`app/db/models.py`) não acompanhou as migrations mais recentes, criando risco real para a próxima migration autogerada.
2. A etapa 0 (base fictícia) já tem conteúdo substantivo no repositório, mas sob nome e local diferentes dos documentados, e isso não está refletido em `status.md`.

Fora esses dois pontos, nenhum código de etapas futuras (3 a 21) foi iniciado antes da hora — `app/channels`, `app/jobs`, `app/core` e `app/llm` não existem, como esperado.

O saneamento é simples (renomear para bater com o que os outros documentos esperam), mas enquanto não é feito é documentação que aponta para o nada.
